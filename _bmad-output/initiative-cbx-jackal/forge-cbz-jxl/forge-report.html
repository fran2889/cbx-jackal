cbz-jxl

Forge report · initiative cbx-jackal · all claims below were measured against libjxl 0.11.1, not recalled

HARDENED. A CLI that turns a comic archive's JPEG pages into JXL pages. One external tool, no Python imaging libraries, order-preserving, atomically written.

What the idea actually is

cbx-jackal book.cbz → book.jxl.cbz. Every JPEG page is re-encoded to JXL; everything else is copied through byte-for-byte. Python entry point, cjxl as the only external tool, verified at startup.

The strongest property is one the original pitch under-sold: lossless output is reversible. cjxl -q 100 embeds JPEG bitstream reconstruction data, so djxl hands back the byte-identical source JPEG — verified by matching SHA-256. Lossless is therefore simultaneously the safest, the reversible, and on this content among the smallest options.

Locked decisions

  • Lossless by default. Bare invocation never destroys quality.
  • Reversibility is exclusive to lossless. -q N<100 drops the reconstruction data and adds a generation of loss permanently.
  • One rule: convert what cjxl can, copy verbatim everything else. A corrupt JPEG is not a special case, just a failed conversion — it gets copied through, same as ComicInfo.xml or a readme.txt.
  • Order = source ZIP stored order, verbatim. No sorting, no renumbering. Readers own the sort, so we never silently reorder a book. This is also why ComicInfo.xml needs no rewriting, and why a skipped page shifts nothing.
  • <name>.jxl.cbz beside the input. Never in-place.
  • Exit non-zero only if a JPEG failed to convert. Non-JPEG pass-throughs are normal and must not make a healthy run look broken.
  • Atomic output. Temp file in the destination directory, then rename. A failed run leaves no output at all, never a partial book. --strict aborts on first failure; --dry-run writes nothing.
  • ZIP entries STORED, not deflated. No --effort (7 measured free). No parallelism.

Encode cost at A4/300dpi: 0.08s per flat comic page, 0.16s per detail-heavy page — a 200-page book is 16–32s serial, which is why page-level parallelism was dropped.

I was wrong, and the pressure-testing is what caught it.

I first dismissed "the original JPEG can be reconstructed" as information-theoretically impossible, and backed it with a sound proof: two JPEGs differing only by an inserted 22-byte comment marker decode to identical pixels, so pixels cannot determine the original bytes. The proof was correct and the conclusion was wrong — the JXL is not pixels-only. It carries extra reconstruction data, and djxl does reproduce the source exactly. The user's original claim held.

Rejected, with reasons

  • Bundling libjxl into the binary — on Linux, two copies of libjxl in one filesystem fight over global JPEG XL decoder handler registration, and the wrong one can win silently.
  • A separate --lossless flag — -q 100 already is lossless; two spellings of one concept.
  • Sidecar .jxl files beside retained JPEGs — superseded once JXL-only proved reversible.
  • Page-level parallelism — nothing to win at 0.08s per page.

Weak points that survived scrutiny

DPI is not stored. jxlinfo reports no density, and 150/300/600 dpi all come back as 72/undefined. Pixel dimensions survive intact (2480×3508). Comic readers size pages by physical DPI, so rendered page size may come out wrong. This needs checking against a JXL-aware reader before the tool claims to be done.

An implementation trap already found. cjxl -q 90 on JPEG input fails with Must not set quality below 100 in combination with --lossless_jpeg=1, which is set by default. Every lossy run must pass --lossless_jpeg=0 as well. Undiscovered, this would have broken every single lossy invocation.

A verification path is now cheap. Because lossless output is reversible, a --verify mode comparing djxl round-trips against the source would be airtight rather than approximate. Worth deciding whether it ships.
