topic: cbx-jackal: CLI converting a comic archive's JPEG pages to JXL, reading ZIP, RAR, CB7 and 7Z, and always writing CBZ
updated: 2026-10-08T10:28
---

- (capability) CAP-1 lossless page conversion by default: converting a JPEG page adds no quality loss and requires no flag. Success: decoding the output .jxl gives pixels identical to decoding the source .jpg (0 differing pixels), and djxl reproduces the source JPEG byte-for-byte.
- (capability) CAP-2 deliberate lossy quality control: an owner who wants smaller files can trade quality on purpose. Success: --quality N<100 yields .jxl pages smaller than lossless output, and the run states the mode so the owner knows reversibility was surrendered.
- (capability) CAP-3 byte-faithful pass-through of every non-converted entry: nothing an owner did not ask to convert is altered, reordered or lost. Success: output entry count and order identical to input, and every non-converted entry byte-identical; no page renumbered or dropped.
- (capability) CAP-4 failure never yields a partial book: an owner is never left holding a truncated archive that looks valid. Success: on any conversion failure either no output file exists, or it exists complete with all entries present, plus non-zero exit and one line per failed page.
- (capability) CAP-5 honest prerequisites: an owner can start the tool and learn precisely what is missing. Success: with cjxl absent, exits non-zero before reading any archive, naming the tool and how to obtain it.
- (constraint) No Python imaging libraries. Container handling is Python standard library only (zipfile).
- (constraint) cjxl is the single external tool and is never bundled into the distribution, because two libjxl copies on one Linux host fight over global decoder handler registration.
- (constraint) Page order is the source ZIP's stored entry order, verbatim. No natural sort, no renumbering, no repair of already-broken ordering. Readers own the sort.
- (constraint) Output is always a new file <name>.jxl.cbz beside the input. Never in-place; never overwrite without an explicit force.
- (constraint) Output is atomic: build to a temp file in the destination directory, then rename. A failed run leaves no output file.
- (constraint) ZIP entries are STORED, never deflated; JXL is already entropy-coded so deflate gains under 1%.
- (constraint) Exit non-zero if and only if a JPEG entry failed to convert. Non-JPEG pass-throughs are normal and must never make a healthy run look failed.
- (decision) Non-goal: reader compatibility. Output is JXL-only and will not display in most comic readers; chosen knowingly after the alternative was weighed.
- (decision) Non-goal: long-term archival preservation. JXL decoder support outside a few libraries is too thin to recommend as a retention format; the case is per-user size and reversibility.
- (decision) Non-goal: bundled or standalone binaries. Non-goal: repairing page order in archives that already have broken ordering.
- (decision) Non-goal: any image manipulation. No resize, rotate, upscale, re-encode of non-JPEG pages, or ComicInfo.xml rewriting. Entry count never changes so <Pages Count> stays correct.
- (assumption) libjxl 0.11.1 behaviour generalises: implicit lossless-transcoding for JPEG input, -q 100 meaning mathematically lossless, and embedded reconstruction data. Verified on this version only.
- (assumption) Python 3 zipfile suffices: reads stored order reliably and writes STORED entries, including ZIP64 for large archives.
- (assumption) cjxl is discoverable on PATH after the preflight message tells the owner how to install libjxl. No vendored copy.
- (question) DPI: jxlinfo reports no density in the JXL (150/300/600 dpi all return 72/undefined via PNG) though pixel dimensions survive (2480x3508). Readers size comic pages by physical DPI. Must the tool record DPI somewhere, or is dropping it accepted? Needs a JXL-aware reader to confirm real impact.
- (question) Should a --verify mode ship in v1? Now that lossless output is byte-reversible, round-tripping through djxl and comparing to the source would be an airtight correctness check rather than an approximate one.
- (question) Which platforms must the preflight message cover? Owner did not state a primary platform; the Windows libjxl install path is the one most likely to need specific wording.
- (note) Evidence base (libjxl 0.11.1, A4@300dpi): lossless 11463 B vs source 22065 B = 48% smaller, byte-identical JPEG recovery. Lossy -q 95 = 14988 B, -q 90 = 11995 B, -q 80 = 9570 B, none reversible. Detail-heavy page: lossless 19.1% smaller. Encode cost 0.08 s flat page, 0.16 s detail-heavy, so a 200-page book is 16-32 s serial.
- (note) cjxl rejects truncated and garbage JPEGs with exit 1 and no output file, so it is a reliable corruption oracle with no silent padding. cjxl also sniffs content rather than extension, so a mislabelled file still converts correctly.

- (capability) CAP-7 read the containers collections actually arrive in: an owner whose library is RAR, CB7 or 7Z converts it without unpacking it by hand. Success: a book in RAR, CB7 or 7Z converts to a CBZ whose entry order, entry count and entry bytes match the source exactly; a corrupt or unreadable source leaves no output at all and exits non-zero; and a run whose only non-CBZ inputs need an absent archiver still converts every other input and exits non-zero.
- (capability) CAP-5 success amended for more than one tool: with a tool the run needs absent, the tool exits non-zero, names every missing tool in a single message, points at the documentation covering linux, mac and windows, and states whether the run stops or only skips the inputs that need it. A tool every run needs stops the run before any archive is opened; one only some inputs need converts the rest and skips those inputs.
- (constraint) Supersedes the earlier stdlib-only container constraint. No Python imaging libraries. Reading and writing ZIP is Python standard library only, via zipfile. Reading RAR, CB7 and 7Z is an external archiver step, because no standard-library module reads them.
- (constraint) The output container is always CBZ and is always written by zipfile, whatever the input container was. No proprietary archiver writer is therefore ever required, and a converted book is indistinguishable from one that arrived as a CBZ.
- (constraint) Supersedes the earlier single-tool constraint. No external tool is ever bundled into the distribution. cjxl is required on every run; every other tool is required only by the severities below. Two libjxl copies on one Linux host fight over global decoder handler registration and the wrong one can win silently, which is why nothing is vendored.
- (constraint) Supersedes the earlier ZIP-specific page-order constraint. Page order is the source container's stored entry order, verbatim: the zipfile order for ZIP, the external archiver's listing order for RAR, CB7 and 7Z. No natural sort, no renumbering, no repair of archives whose ordering is already wrong. Readers own the sort; the tool never silently reorders a book.
- (constraint) Supersedes the earlier STORED wording, which read as a claim about the input. Entries in the output are STORED, never deflated, because the output is always a ZIP. The input's own compression is not preserved: re-inserting one member of a solid archive recompresses the whole block, so entry-level byte fidelity holds while the source's internal container layout does not.
- (constraint) Supersedes the earlier exit-code constraint, which named only a failed JPEG entry and already disagreed with the shipped code. The exit code is non-zero when a JPEG entry failed to convert, when a source could not be read, and when a tool the run needed was absent or an existing output was refused. Non-JPEG pass-throughs are normal and must never make a healthy run look failed. One refused path does not abandon the rest of the list.
- (decision) The preflight carries two severities. A tool every run needs is checked before any archive is opened and its absence stops the run. A tool only some inputs need is decided from the expanded input set, by the recognised input suffix rather than by sniffing, and its absence converts the rest of the list and skips only the inputs that needed it, with a non-zero exit. One message names every missing tool whatever the count. A dry run needs exactly the tools the real run would, because it encodes every page in order to report real size figures.
- (assumption) Supersedes the earlier zipfile-suffices assumption. Python 3 zipfile suffices for the output container and for reading ZIP: it reads stored entry order reliably and writes STORED entries, including ZIP64 for large archives. It does not read RAR, CB7 or 7Z, and nothing in the standard library does.
- (assumption) Supersedes the earlier cjxl-on-PATH assumption, which named one tool. External tools are expected on PATH, or discoverable once the preflight names them and points at the documentation. No vendored copy of any of them.
- (note) Measured for the container capability: 7z reads rar, cb7 and 7z by content rather than by extension, extraction is byte-exact, and 7z l returns rc 2 on a broken archive, so the failure oracle keeps the shape cjxl already has. Writing is unaffected because the output is always CBZ.
- (question) Encrypted or password-protected archives are unaddressed. Should such an input be refused with an owner-facing message naming the password, skipped the way a missing tool is skipped, or passed through untouched? RAR and 7Z both support encryption and comic collections containing it are common, so the tool will meet them.
